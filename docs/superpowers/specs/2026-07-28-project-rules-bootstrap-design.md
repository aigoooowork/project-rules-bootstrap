# Project Rules Bootstrap 设计规范

## 1. 目标

`project-rules-bootstrap` 是一个面向新项目接入和新人使用场景的可复用 Codex Skill。它通过只读扫描、证据分类、渐进式询问和人工确认，为不同技术栈的项目建立一套可维护的 AI 编程规则体系。

本 Skill 不替用户决定团队规则。它负责发现项目事实和候选规则、解释依据、暴露冲突，并在获得明确确认后生成规则文件。

首版以 Codex Skill 形式发布，同时为 Codex、Claude Code、Cursor、Trae、CodeBuddy、WorkBuddy 及其他工具生成适配入口。

## 2. 核心原则

1. 不根据通用经验冒充项目事实。
2. 无法从代码、配置或文档可靠判断的关键内容必须询问用户。
3. “禁止、必须、不得”等强约束必须经过额外确认。
4. 任何目标项目文件写入前都必须获得用户确认。
5. 已有规则只能增量合并，不得无确认覆盖或整文件重写。
6. 正式规则按领域拆分，入口文件保持简短，减少无关上下文。
7. 只把有官方或可验证依据的适配标记为自动加载；其余适配必须说明手动导入方式。
8. 扫描不得读取密钥正文、执行项目代码、安装依赖或访问远程仓库。

## 3. 范围

### 3.1 首版包含

- 前端、后端、全栈、Monorepo 及其他常见项目结构识别；
- 技术栈、目录职责、编码模式、测试方式和已有规则发现；
- 事实、惯例、强约束候选、未知项和冲突项分类；
- 风险驱动的渐进式问答；
- 初始化和增量更新流程；
- 多工具入口适配；
- 共享规则 Manifest；
- Python 标准库扫描器和输出验证器；
- 单元测试、行为评估和中英文发布文档。

### 3.2 首版不包含

- 完整独立 CLI；
- 自动安装依赖；
- 自动执行构建、测试或项目代码；
- 自动创建或推送 GitHub 仓库；
- 未经确认自动修改规则；
- 为没有可靠依据的平台声称自动加载；
- 云端规则管理服务。

## 4. 用户角色

初始化时询问当前身份：

- 项目负责人；
- 项目成员；
- 新加入项目的开发者。

角色只影响说明详细度、建议内容和确认提示，不自动赋予权限。普通成员或新人新增团队级强约束时，应提示需要项目负责人确认。

更新流程开始时展示上次角色并询问是否变化。角色可以随项目熟悉程度变化，但身份变化不会自动放宽强约束确认。

个人角色属于本地运行状态，默认不写入团队共享 Manifest。

## 6. 目标项目输出

```text
target-project/
├── RULES.md
├── AGENTS.md                         # 选择 Codex 时
├── CLAUDE.md                         # 选择 Claude Code 时
├── .cursor/rules/...                 # 选择 Cursor 时
├── .trae/rules/...                   # 选择 Trae 时
├── .codebuddy/rules/...              # 选择 CodeBuddy 时
└── .ai/
    ├── rules.analysis.md
    ├── rules-manifest.json
    ├── rules/
    │   ├── project.md
    │   ├── architecture.md
    │   ├── coding-style.md
    │   ├── frontend.md
    │   ├── backend.md
    │   ├── api.md
    │   ├── database.md
    │   ├── testing.md
    │   ├── security.md
    │   └── restrictions.md
    └── cache/
```

仅生成适用的领域文件。`.ai/rules/` 是唯一共享规则源；工具入口负责按任务引导读取相关规则。`RULES.md` 是面向人类和通用工具的短入口，不声称被所有工具自动加载。

正式规则和 Manifest 建议进入 Git。`rules.analysis.md` 是否提交由用户选择。`.ai/cache/` 保存本地扫描状态，默认加入 `.gitignore`，不得保存源码正文、密钥或个人身份信息。

## 7. 初始化工作流

### 7.1 只读预检

- 定位项目根目录；
- 检查已有规则、Git 状态和项目规模；
- 识别依赖目录、构建产物和疑似敏感路径；
- 不创建目标项目文件。

### 7.2 基础选择

- 询问当前角色；
- 询问使用的 AI 编程工具，支持多选和全部生成；
- 确认输出语言；
- 使用推荐扫描范围，避免要求新人逐目录配置。

### 7.3 项目扫描

扫描器采集目录、配置、依赖、测试、文档、已有规则和有限 Git 信息。扫描器只提供证据，不生成规则结论。

### 7.4 分析分类

- `fact`：代码或配置直接证明；
- `convention`：重复出现但仍需确认的项目习惯；
- `constraint-candidate`：可能限制开发行为的候选；
- `unknown`：无法可靠判断；
- `conflict`：代码、文档或已有规则互相矛盾。

### 7.5 渐进式询问

优先解决架构职责、数据访问、接口边界、安全和依赖策略等高影响问题。

问题通常控制在五至十个，必要时分两轮。低风险问题按主题合并，高风险问题单独询问。证据充分时减少问题，不为达到固定数量而提问；仍存在高风险歧义时不能为了减少操作而跳过确认。

### 7.6 分析文件写入门槛

先在对话中展示分析摘要和拟创建文件。用户确认后才写入 `.ai/rules.analysis.md`。

### 7.7 内容确认

- 低风险事实集中确认；
- 普通惯例按领域分组确认；
- 强约束默认逐条确认；
- 只有用户主动选择时，才允许批量确认语义相近的强约束；
- 批量确认前必须展示完整范围和风险；
- 未解决的未知项和冲突项不得进入正式规则。

### 7.8 最终写入门槛

展示将新增、修改、保持不变和无法自动合并的文件。用户明确确认后才写入正式规则和工具入口。

### 7.9 验证

校验入口引用、规则作用域、Manifest、重复内容、适配等级和强约束确认状态。最终分别报告已完成、待确认、未生成和仅支持手动导入的内容。

## 8. 更新工作流

1. 读取上次 Manifest、扫描基线和工具选择；
2. 询问用户当前身份是否变化；
3. 优先根据上次确认的 Git 提交点分析增量；
4. 在缺少基线、主要技术栈改变、项目结构大幅变化或用户要求时完整扫描；
5. 输出新增、修改、废弃和冲突候选；
6. 对语义发生变化的规则重新确认；
7. 再次执行内容确认和写入确认；
8. 更新 Manifest 和本地缓存。

没有 Git 时仍可完整扫描，但必须说明无法执行提交点增量分析。

## 9. 规则数据模型

每条规则具有稳定 ID：

```json
{
  "id": "backend.repository-boundary",
  "type": "constraint",
  "domain": "backend",
  "scope": ["backend/**"],
  "statement": "数据库访问应通过 repository 层完成。",
  "evidence": [
    {
      "path": "backend/repositories/user_repository.py",
      "kind": "code-pattern"
    }
  ],
  "confidence": "medium",
  "status": "confirmed",
  "confirmation": {
    "mode": "individual",
    "confirmed_at": "ISO-8601 timestamp"
  }
}
```

约束：

- `type` 只允许 `fact`、`convention`、`constraint`；
- `unknown` 和 `conflict` 只存在于分析阶段；
- `scope` 明确目录或模块边界；
- `evidence` 只记录必要路径和证据类型；
- `confidence` 使用 `high`、`medium`、`low`；
- 强约束只有确认后才能进入 `restrictions.md`；
- 默认不记录确认人的姓名、邮箱或 Git 身份。

## 10. 规则内容契约

不同模型和工具必须生成相同的项目规则语义。模型或工具差异只能改变入口格式、加载语法和作用域元数据，不能改变项目事实、规则含义或确认状态。

### 10.1 共享结构

每个正式规则模块使用以下结构：

```md
# 规则领域名称

## 适用范围

## 已确认事实

## 执行规则

## 验证方式

## 相关规则
```

存在强约束时才增加：

```md
## 已确认的强约束
```

每条规则应具有明确行为和适用范围；需要时补充原因、验证方式和 Manifest 规则 ID。

### 10.2 通用禁止内容

正式规则不得包含：

- 从通用经验推导、却被描述成项目事实的内容；
- 未确认的“禁止、必须、不得”；
- 大段源码；
- 密钥、账号、内部地址等敏感内容；
- 与当前领域无关的规则；
- “保持代码质量”等不可执行的空泛表达；
- 同一规则在多个文件中的重复副本；
- 工具专用语法；
- 角色人格提示；
- 未来架构设想冒充的当前事实；
- 未标记为历史或废弃的失效规则。

### 10.3 领域文件契约

| 文件 | 应包含 | 不应包含 |
|---|---|---|
| `project.md` | 项目类型、技术栈、主要目录、启动构建命令、关键文档 | 详细编码规范、推测的业务规则 |
| `architecture.md` | 模块职责、依赖方向、主要数据流、扩展位置 | 具体代码格式、未经确认的目标架构 |
| `coding-style.md` | 已观察并确认的命名、格式、错误处理和注释习惯 | 单纯复制语言官方规范 |
| `frontend.md` | 页面、组件、状态、请求层、路由和样式约定 | 后端数据库规则、通用框架教程 |
| `backend.md` | 接口层、服务层、数据访问层、事务和异常边界 | 前端组件规则、无证据的分层禁令 |
| `api.md` | 路由、请求响应、鉴权、错误结构和兼容要求 | 数据库实现细节、通用 API 教程 |
| `database.md` | 数据访问入口、迁移方式、SQL 方言和事务约定 | 连接凭证、未经验证的生产信息 |
| `testing.md` | 测试目录、命令、层级、夹具和通过标准 | 未确认的覆盖率或测试强制指标 |
| `security.md` | 已确认的认证、敏感数据和安全处理边界 | 大段通用安全清单、漏洞细节和密钥 |
| `restrictions.md` | 已确认强约束的范围、原因、例外和验证 | 候选规则、推测规则和普通编码习惯 |

只有适用且具有内容的领域文件才生成。

### 10.4 工具入口契约

工具入口只负责：

1. 声明共享规则位置；
2. 指示如何按任务选择相关规则；
3. 提供该工具所需的作用域元数据；
4. 说明适配属于自动加载、支持导入还是手动引用。

工具入口不得：

- 改写共享规则含义；
- 自行增加约束；
- 完整复制全部共享规则；
- 因模型不同而改变项目事实；
- 混入其他工具的专用配置。

各工具特有内容：

- `AGENTS.md`：提供面向 Codex 的任务到规则文件路由；
- `CLAUDE.md`：使用 Claude Code 支持的文件导入语法；
- Cursor `.mdc`：提供 `description`、`globs` 和加载类型元数据；
- Trae：使用精简的领域入口，避免规则上下文过长；
- CodeBuddy：使用 `RULE.mdc` 结构和加载类型；
- WorkBuddy：提供明确的手动 `@` 引用说明；
- `RULES.md`：作为人类和通用工具的短导航页。

### 10.5 模板要求

`assets/templates/rules/` 为每个领域提供模板，`assets/templates/adapters/` 为每个工具提供入口模板。每个模板明确：

- 必填章节；
- 条件章节；
- 禁止内容；
- 建议长度；
- 来源要求；
- 强约束确认要求；
- 一个正确示例；
- 一个典型错误示例。

模板是输出契约，不是让模型填充无内容章节的表格。缺少可靠内容时省略相应模块。

### 10.6 验证要求

输出验证器必须检查：

- 是否缺少适用范围；
- 是否存在无来源或未确认的强约束；
- 是否把工具专用语法写入共享规则；
- 是否出现明显跨领域内容；
- 是否存在规则正文重复；
- 是否包含不可执行的空泛规则；
- 工具入口是否复制大量共享规则；
- 入口的加载声明是否与适配器等级一致。

## 11. 分析文件

`rules.analysis.md` 包含：

1. 项目画像；
2. 已证实事实；
3. 待确认惯例；
4. 强约束候选；
5. 冲突项；
6. 暂缓的低影响问题；
7. 拟生成文件。

默认不超过约三百行。超过时按模块拆分附录。相同模式合并展示，不粘贴大段源码，用户可按需展开证据。

## 12. 扫描器设计

### 12.1 技术约束

- Python 标准库实现；
- 目标支持 Python 3.9 及以上；
- 不依赖 pip、npm 或外部服务；
- 没有 Python 时退化为 AI 使用文件搜索和 Git 工具完成扫描；
- Windows、macOS 和 Linux 使用相同的数据结构。

### 12.2 扫描范围

- 项目与子模块边界；
- 有限深度目录结构；
- 依赖、构建、格式化、Lint、测试、CI/CD 和部署配置；
- 主要模块入口和代表性源文件；
- 架构、贡献和现有规则文档；
- 本地 Git 分支、近期提交摘要和变更范围。

### 12.3 安全边界

默认不读取以下文件正文：

- `.env` 和环境变量文件；
- 私钥、证书、令牌及凭证文件；
- 数据库转储；
- 大型日志；
- 二进制文件；
- 依赖与构建产物；
- 指向项目外部的符号链接。

扫描器不访问网络、不安装依赖、不执行项目代码或构建脚本。结构化结果优先输出到标准输出；过大时只使用系统临时目录。

### 12.4 证据政策

- 单个样例不能证明团队惯例；
- 配置文件通常比零散代码样例更强；
- 文档与代码一致时可提升置信度；
- 文档与实现冲突时进入 `conflict`；
- 未观察到某行为不能推出“禁止该行为”；
- 通用最佳实践只能作为建议，不能成为项目事实。

## 13. 已有规则合并

1. 读取已有入口和规则文件；
2. 识别相同、互补、冲突和无法判断的内容；
3. 展示拟新增、拟保留和冲突待决清单；
4. 用户确认后只更新明确的托管区块；
5. 无法安全定位托管区块时生成候选文件或补丁说明；
6. 不覆盖整个文件；
7. 已有强约束也需重新确认后才能进入共享规则源。

## 14. 工具适配器

适配器状态：

- `native-auto`：官方确认自动加载；
- `import-supported`：官方确认支持导入；
- `manual-reference`：需要用户显式引用；
- `unverified`：当前无法可靠确认。

首版适配目标：

| 工具 | 入口 | 状态 |
|---|---|---|
| Codex | `AGENTS.md` | `native-auto` |
| Claude Code | `CLAUDE.md` | `native-auto` |
| Cursor | `.cursor/rules/*.mdc` | `native-auto` |
| Trae | `.trae/rules/*.md` | `native-auto` |
| CodeBuddy | `.codebuddy/rules/<rule>/RULE.mdc` | `native-auto` |
| WorkBuddy | `RULES.md` 或 `.ai/rules/*` | `manual-reference` |
| 其他工具 | `RULES.md` | `manual-reference` |

`adapters.json` 记录工具 ID、显示名称、路径、作用域能力、导入能力、核验日期和官方来源。初始化只生成用户选中的适配器；用户可以选择全部生成。

内置资料可能过期时必须提示。联网不是必需条件；如果当前环境允许并且需要刷新，只使用官方资料。未经验证的能力不得升级为自动兼容。

## 15. 测试策略

### 15.1 单元测试

使用 `unittest` 验证：

- 根目录识别；
- 技术栈信号；
- Monorepo 边界；
- 忽略目录和敏感文件；
- 项目外符号链接；
- Git 增量范围；
- 已有规则发现；
- Manifest 结构；
- 适配器模板；
- 共享规则内容契约；
- 工具入口内容契约；
- 跨领域内容和重复规则检测；
- 未确认强约束无法通过验证。

### 15.2 Skill 行为评估

遵循先基线、后 Skill 的测试顺序。

首轮三个场景：

1. 高歧义 Monorepo；
2. 已有多工具规则的项目；
3. 包含强约束候选和敏感文件的后端项目。

核心断言：

- 写入前获得确认；
- 正确区分规则类型；
- 每项规则具有来源；
- 未知项不进入正式规则；
- 不覆盖已有文件；
- 不读取敏感文件正文；
- 正确生成所选适配入口；
- 手动适配被诚实标注；
- 不同工具入口保持相同规则语义；
- 共享规则不包含工具专用语法；
- 工具入口不复制大量规则正文；
- 更新时询问身份变化；
- 正式规则中不存在未确认强约束。

评估结果使用 `skill-creator` 提供的静态审阅页面呈现。首轮通过后再扩展前端、无 Git、无 Python、角色变化和其他适配器场景。

## 16. 发布策略

- Skill 核心指令使用简洁英文；
- 与用户交互时跟随用户语言；
- 提供英文 `README.md` 和中文 `README.zh-CN.md`；
- 同一目标项目只生成一种规则语言；
- 文件名保持英文；
- 采用 Apache License 2.0；
- 提供安装、使用、适配矩阵和贡献指南；
- 不自动创建远程仓库或推送 GitHub。

## 17. 成功标准

1. 新人能在不理解项目全部细节的情况下完成引导流程；
2. 高风险未知项不会被默认猜测；
3. 强约束不会在无明确确认时进入正式规则；
4. 已有规则不会被无确认覆盖；
5. 同一共享规则可为多个工具生成准确入口；
6. 大型项目不会生成单个超长入口文件；
7. 后续更新能基于 Git 增量工作并重新确认身份；
8. 无 Python、无 Git或缺少原生适配时能够诚实降级；
9. 单元测试和行为评估能够验证以上关键边界。
10. 不同模型生成的规则结构和语义保持在同一内容契约内。
