# Project Rules 双 Skill 内容优先改造设计

## 1. 背景

当前 `project-rules-bootstrap` 的安全写入、规则归属、Manifest、Adapter 和回滚架构较完整，但生成内容的信息密度不足。

现有发现流程主要读取依赖清单、项目入口和已有规则文件。普通业务源码多数只进入文件清单，没有被用于横向比较和完整调用链追踪。因此生成结果容易停留在：

- 项目使用某种语言或框架；
- 存在某些目录；
- 遵循通用格式化工具；
- 不硬编码密钥；
- 使用良好实践。

这些内容无法回答新成员或新 AI 最关心的问题：同类代码应该放在哪里、模仿哪个现有实现、沿用什么调用方式、复用哪些公共能力，以及修改后如何验证。

本次改造保留现有安全架构，将产品重心从“规则文件审计器”调整为“项目工作方式发现器”。

## 2. 核心目标

安装包为现有仓库生成可供新成员、新 AI 直接执行的项目工作手册，使新增或修改的代码在以下方面与现有项目保持一致：

- 文件和模块落点；
- 调用链与依赖方向；
- 命名、日志、异常、返回和注释风格；
- 公共方法、组件和基础能力复用；
- 请求、字段和状态的跨层传递；
- 数据访问、外部集成和安全边界；
- 测试、构建和验收方式。

最终效果应让连续修改看起来像由同一个团队、同一个 AI 完成，而不是每次重新套用一套通用最佳实践。

## 3. 非目标

本次改造不把 Skill 变成：

- 架构说明书生成器；
- 通用最佳实践审计器；
- 自动重构建议器；
- 仅适用于 Python、Flask 或 Vue 的框架模板；
- 完整静态分析器或精确调用图构建器；
- 无需证据即可生成强约束的政策工具。

架构、目录和技术栈是寻找项目规则的证据，不是主要成果。只有当架构事实能指导代码落点、依赖方向、共享影响面或验证方式时，才进入正式规则。

## 4. 安装与 Skill 结构

项目改造为一个安装包中的两个独立 Skill：

```text
project-rules-bootstrap/
├── .codex-plugin/
│   └── plugin.json
├── skills/
│   ├── project-rules-init/
│   │   └── SKILL.md
│   └── project-rules-update/
│       └── SKILL.md
├── core/
│   ├── references/
│   ├── templates/
│   └── scripts/
├── evals/
└── tests/
```

安装包和仓库继续使用 `project-rules-bootstrap` 名称。旧的单一 `project-rules-bootstrap` Skill 不再作为第三个入口，避免代理继续走初始化与更新混合的旧流程。

两个 Skill 共享同一套发现、内容契约、Manifest、Adapter、安全写入和验证实现，避免规则语义或安全行为分叉。

## 5. `project-rules-init`

### 5.1 触发条件

用于：

- 初始化、建立或首次生成项目 AI 规则；
- 仓库中不存在可信的 `project-rules-bootstrap` Manifest；
- 需要让新成员、新 AI 理解并沿用现有项目工作方式。

### 5.2 职责

1. 识别仓库模块、语言、构建系统和源码角色。
2. 对主要模块进行分层抽样。
3. 追踪有代表性的完整代码链。
4. 横向比较同类代码，识别稳定项目模式。
5. 将模式转换成可执行规则。
6. 展示一次以内容为主的预览。
7. 在正常情况下经一次确认写入 canonical rules、Manifest 和选定 Adapter。

### 5.3 边界

若发现可信的既有 Manifest 和规则集，Init 不重新初始化或覆盖，而是说明当前状态并引导使用 `project-rules-update`。

## 6. `project-rules-update`

### 6.1 触发条件

用于：

- 更新、同步或刷新已有项目规则；
- 代码、调用链、模块职责或项目惯例发生变化；
- 现有规则可能与当前实现产生漂移。

### 6.2 职责

1. 验证既有 Manifest、canonical rules 和 Adapter 归属。
2. 优先读取 Git 差异和已有扫描基线。
3. 从变化点向入口、调用方、下游依赖和测试追踪。
4. 识别规则的保留、新增、修改、废弃或冲突状态。
5. 只展示规则语义变化和受影响范围。
6. 无冲突时经一次确认完成增量更新。

### 6.3 边界

若不存在可信基线，Update 不把首次导入伪装成增量更新，而是引导使用 `project-rules-init`。

## 7. 项目证据优先原则

### 7.1 稳定历史模式

项目中大量、稳定存在的写法默认视为项目约定，即使它与通用现代最佳实践不同。Skill 的职责是让后续代码与项目保持一致，而不是擅自推动现代化。

以下证据可直接建立项目惯例：

- 两个以上可比较位置采用同一写法；
- 一个明确的项目规则文档；
- 一个有效配置加一个实际调用点；
- 一条稳定调用链中的多个连续环节共同证明同一规则。

普通事实和稳定惯例不逐项询问用户。

### 7.2 需要询问的对错题

只有以下情况暂停并请求决策：

- 两套可信的现行写法直接冲突；
- 现有文档与实际运行代码相反；
- 可能导致权限绕过、敏感数据泄露、数据损坏或不可逆行为；
- 用户提出项目中不存在的新强制禁令；
- 证据不足，继续生成会明显误导新 AI。

通用最佳实践与稳定项目写法不同，本身不构成冲突。

## 8. 跨语言完整代码链发现

### 8.1 通用链路模型

发现流程不预设框架分层，而是识别项目中实际存在的角色：

```text
用户入口或外部事件
→ 页面、CLI、HTTP、消息、任务或库入口
→ 路由、Controller、Handler、Resource 或命令分发
→ 参数解析、DTO、Schema 和输入校验
→ 业务编排、Service、Use Case、领域函数或核心包
→ Repository、DAO、Mapper、SQL、ORM 或外部服务
→ 数据库、缓存、文件、消息队列或第三方系统
→ 返回转换、状态更新和用户反馈
→ 对应测试、构建与验收
```

同时横向识别：

- 配置与环境；
- 认证与权限；
- 错误和返回；
- 日志与监控；
- 公共方法和共享组件；
- 测试、构建和部署。

### 8.2 语言与框架

语言和框架只决定证据形式，不改变发现目标：

- Python/Flask：Blueprint、Resource、parser、中间件、业务函数和数据库 helper；
- Vue/React：页面、组件、路由、状态、请求层、样式和构建配置；
- Java/Spring：Controller、DTO、Service、Repository、Mapper、配置和测试；
- Go：router、handler、service、repository、package、middleware 和测试；
- Node/Nest/Express：module、controller/router、service、middleware 和 client；
- CLI、SDK、脚本、数据任务或纯库：识别真实入口、核心调用路径、输入输出边界和测试方式。

对未知语言，仍通过文件角色、导入关系、调用方、配置和测试关系进行通用追踪，不虚构框架语义。

### 8.3 分层抽样

扫描器按模块和文件角色分配内容预算，而不是把第一个目录读深后耗尽预算。

每个主要模块优先选择：

- 入口或路由文件；
- 一个或多个代表性业务实现；
- 数据或外部集成入口；
- 公共能力调用点；
- 对应测试；
- 与该链路直接相关的配置。

同类文件需要横向比较。只识别技术栈但未追踪至少一条代表性完整代码链，视为发现失败。

### 8.4 安全边界

继续保持：

- 敏感路径只记录存在性，不读取正文；
- 不执行目标项目代码、构建、测试、Hook 或包脚本；
- 不安装依赖或拉取远程内容；
- 不跟随指向仓库外的符号链接；
- 跳过二进制、依赖目录、构建产物和缓存；
- 对跳过、截断和无法访问的范围明确标记。

## 9. 规则内容模型

### 9.1 面向任务组织

最终内容回答新 AI 的实际问题：

- 第一次进入仓库先读什么；
- 同类功能通常落在哪里；
- 应模仿哪个已有实现；
- 请求、字段和状态如何跨层传递；
- 哪些公共能力不能重造；
- 项目实际使用什么命名、异常、日志和返回风格；
- 修改共享代码需要检查哪些消费者；
- 改完至少验证什么；
- 哪些边界属于明确红线。

### 9.2 单条规则结构

每条正式规则至少包含：

1. **适用范围**：目录、文件类型、模块或任务类型。
2. **执行动作**：新 AI 应具体怎么做。
3. **项目锚点**：可模仿的路径、符号、公共方法或现有链路。
4. **验证方式**：真实命令、搜索目标或对照点。

示例：

```text
规则：新增同类业务接口

适用范围：
- backend/app/{module}/**

怎么写：
- Resource 放在 res_*.py。
- 参数解析复用或新增 parsers.py。
- 路由在 views_resource.py 的 RES_LST 中注册。
- Resource 只负责取参、连接获取、业务调用和统一返回。

模仿位置：
- backend/app/preparation/res_preparation.py
- backend/app/preparation/views_resource.py

验证方式：
- 检查路由注册位置。
- 运行对应接口测试和项目已有分层检查。
```

### 9.3 Canonical 文件职责

- `project.md`：首次进入项目的阅读入口、任务导航和真实运行方式。
- `architecture.md`：只记录会影响代码落点、依赖方向和共享影响面的边界。
- `coding-style.md`：从重复代码提取命名、文件组织、日志、异常、注释和格式习惯。
- `frontend.md`：页面、组件、状态、请求、路由和样式的实际项目模式。
- `backend.md`：接口层、业务层、公共能力和数据访问的实际写法。
- `api.md`：参数来源、跨层契约、返回结构、Token、错误和兼容方式。
- `database.md`：连接入口、SQL/ORM helper、参数、表名、迁移、分页和事务方式。
- `testing.md`：改动类型对应的测试位置、运行目录、真实命令和通过标准。
- `security.md`：项目实际存在的鉴权、权限和敏感数据边界。
- `restrictions.md`：真正的项目红线，不汇总普通习惯。

只生成有可靠、可执行内容的领域文件，不为凑齐领域生成空文件。

## 10. 内容质量门槛

以下内容不能单独成为正式规则：

- “项目使用 Flask / Vue / Java / Go”；
- “保持代码整洁”；
- “遵循项目风格”；
- “采用分层架构”；
- “编写高质量测试”；
- “遵循安全最佳实践”。

正式规则必须满足：

- 至少包含一个项目路径、符号、公共方法或真实命令；
- 能直接改变新 AI 的下一步行动；
- 不只说明禁止事项，还给出项目中的正确替代方式；
- 架构事实能推导出代码落点、依赖方向或影响面；
- 验证方式在当前项目中真实存在或明确标为人工对照；
- 规则的适用范围与证据范围一致；
- 不把未来目标描述成当前事实。

生成预览前执行内容质量检查。若主要模块只有技术栈描述而没有工作配方，Init 不得宣称分析完成。

## 11. 自适应审计与确认

### 11.1 正常模式

正常初始化或更新流程只保留一次面向内容的确认：

1. Skill 完成只读发现。
2. 展示准备生成或修改的具体规则及其适用范围。
3. 用户确认后一次写入 canonical rules、Manifest 和 Adapter。

不再默认询问：

- 用户是负责人、成员还是新人；
- 已由项目证据回答的普通事实；
- 稳定存在的项目惯例；
- 是否接受通用最佳实践；
- 每个文件的审计分类。

生成内容始终面向新成员、新 AI。规则语言默认跟随当前对话语言，用户另有指定时覆盖默认值。

### 11.2 严格模式

发现以下条件时，只对相关部分升级严格审计：

- 强约束；
- 可信规则冲突；
- 敏感或数据安全边界；
- 无法证明归属的既有规则文件；
- 不安全覆盖；
- 证据不足且会产生误导。

未受影响的普通规则继续按正常模式处理，不因一个局部风险让整个流程退化为全面审计。

### 11.3 内部安全机制

Manifest、哈希、所有权、原子写入、回滚和恢复日志继续保留，但作为内部实现，不占用用户交互主流程。最终报告只需区分：

- 已生成或已更新；
- 因冲突待确认；
- 未验证范围；
- 需要手动加载的 Adapter。

## 12. Adapter

Adapter 继续保持轻量，只负责引导助手读取 canonical rules，不复制或改写规则语义。

安装包中的两个 Skill 共享同一个可信 Adapter registry。Init 创建已选 Adapter；Update 只更新已托管且仍被选择的 Adapter。未验证的工具不虚构路径或自动加载能力。

## 13. 评估设计

### 13.1 失败基线

当前 `ch_apis_000` 生成结果作为首个真实失败基线：

- 只识别 Flask 和少量入口；
- `coding-style.md` 只有 Black；
- 未识别 Blueprint、路由表、Resource、parser、中间件顺序、`flask.g`、统一返回和 `ywutils`；
- 生成的数据库隔离规则与实际 Resource 直接获取连接的代码冲突。

改造前必须用测试或评估固定这些失败，避免只修改文档而没有行为证明。

### 13.2 评估样本

至少覆盖：

1. 旧式 Python/Flask 项目；
2. Vue + Flask 复杂全栈项目；
3. Java 分层项目；
4. Go 服务项目；
5. 多模块或混合技术栈项目；
6. CLI、库或非 Web 项目；
7. 存在可信冲突或安全风险的项目；
8. 已有规则集的增量更新项目。

样本使用可提交的非敏感 fixture，不依赖用户本地绝对路径。

### 13.3 质量断言

评估同时检查安全性和内容价值：

- 普通初始化只出现一次写入确认；
- 不询问用户角色；
- 不要求确认稳定重复模式；
- 至少追踪一条代表性完整代码链；
- 主要模块得到公平抽样；
- 正式规则包含适用范围、执行动作、项目锚点和验证方式；
- 空泛规则数量为零；
- 规则引用真实存在的路径、符号或命令；
- 跨端项目能识别至少一条前后端契约链；
- 更新只展示规则语义变化；
- 只有真实冲突、安全风险或不安全覆盖触发严格审计；
- 敏感内容、外部链接和目标项目执行仍被禁止。

### 13.4 对比方式

改造前版本作为基线，改造后版本作为候选。对同一 fixture 比较：

- 规则具体性；
- 项目锚点覆盖；
- 完整代码链覆盖；
- 新 AI 可执行性；
- 空泛内容数量；
- 交互次数；
- 安全边界保持情况。

## 14. 迁移策略

1. 保留当前实现快照作为旧 Skill 基线。
2. 先增加失败评估，证明旧版本在规则内容上不足。
3. 建立一个安装包、两个 Skill 的目录和触发边界。
4. 抽取共享核心，不在两个 Skill 中复制规则语义。
5. 扩展扫描器的跨语言、分层抽样和代表链路候选输出。
6. 重写内容契约和模板，使单条规则成为工作配方。
7. 将两道默认写入关口改为一次内容确认，保留风险升级分支。
8. 完成 Init 评估后再完成 Update 评估。
9. 验证安装包包含两个可发现 Skill，且旧单 Skill 不再触发。

## 15. 验收标准

改造完成需同时满足：

- 一个安装包能够发现 `project-rules-init` 和 `project-rules-update`；
- 两个 Skill 使用同一份共享核心；
- Init 能从多语言项目中发现完整代码链和稳定项目规则；
- Update 能根据差异更新受影响规则而不做完整重复审计；
- 新 AI 能仅依赖生成规则判断同类代码的落点、模仿对象、复用方式和验证方法；
- `ch_apis_000` 型样本不再只生成 Flask、Black 和通用安全口号；
- `xm_bzhjswyh` 型样本能体现阅读入口、跨端边界、公共能力复用、共享影响面、数据库口径和真实验证命令；
- Java、Go、CLI/库样本不被强套 Flask 或 Web 分层；
- 正常流程只有一次内容确认；
- 高风险条件仍能局部升级严格审计；
- 现有敏感信息保护、安全写入、所有权验证和回滚能力不退化；
- 全部单元测试、契约测试和行为评估通过。
